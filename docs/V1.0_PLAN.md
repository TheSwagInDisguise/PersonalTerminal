# V1.0 plan — confirmed decisions (0.5.0 release)

This is the source of truth for the V1.0 planner bundle. It records the decisions confirmed for
the **0.5.0** release and the boundaries that must not be overstated in other docs.

## Shipped in 0.5.0

### Planner: one-off work, separate from habits
A one-off task is **not** a habit. It has no streak, schedule, XP or widget. It has:

- a project (`planner_projects`) with Markdown notes and a colour;
- a priority (`low / normal / high / urgent`), an optional due **date** and an optional exact
  **reminder** alarm (`PlannerReminderReceiver`);
- a newline-separated **checklist** with per-item tick state;
- Markdown notes with a live, read-only **preview** (headings, ordered/bulleted lists, task boxes,
  quotes, code, tables, rules, bold/italic/strikethrough/links/images) — no WebView, no HTML execution;
- **contextual links** (`pt://habit/…`, `pt://watch/…`, `pt://task/…`, `pt://project/…`,
  `pt://note/…`) and **attachments** (content/file URIs), rendered as chips that open in-app or
  through `ACTION_VIEW`.

Room schema **11** adds `planner_projects`, `planner_tasks` and `planner_notes`; `MIGRATION_10_11`
is additive only. Schema `10.json` was generated and committed first (the 0.4.2 `sync_log`
schema had been missing from the repo), then `11.json`. Both are in `app/schemas/…`.

### Backup / restore: FULL watch media contents
Backup payload schema **7** is backwards compatible (every new field is optional). An archive now
contains:

- the profile photo and every wrist shot;
- **every** `watch_photos` gallery row;
- **every** `watch_documents` receipt / warranty / attachment — the actual bytes, not just the row.

Media is namespaced as `media/photos/…` and `media/docs/…`; pre-0.5.0 `media/<name>` entries are
still read as photos. `verifyArchive` audits both kinds; `restoreArchive` reinstalls both kinds.
`clearAllData()` now clears the planner tables and the sync journal on a full restore.

### Onboarding: restore / link / merge
First launch supports **three** explicit paths, never a silent choice:

1. **restore** — replace this install with a Drive archive (existing 7.1 behaviour);
2. **link** — keep every local row and remember the Drive account + backup folder
   (`DriveSync.linkAccount`);
3. **merge an independent install** — download a Drive archive and merge it into the data already
   on this device (`BackupManager.mergeArchive`). Primary keys are offset past the local maximum
   and all child references are remapped, so both installs' habits, watches and planner items
   survive. Local preferences are kept and existing media files are not deleted.

### Drive Markdown is two-way editable
Planner notes are mirrored as plain `.md` files in the Drive backup folder. They can be edited in
the app or directly in Drive. `NoteMarkdownSync` keeps `lastSyncedBody` as the common base:

- only Drive changed → apply the Drive text locally;
- only the app changed → keep the local text and push it;
- unchanged → no write.

**Conflicting note sync pauses for user choice while retaining both versions.** When both sides
changed, note sync is paused, the Drive text is stored in `pendingRemoteBody`, the local text stays
in `body`, and the planner UI shows both with `keep local / use drive / keep both`. Both versions
are also recorded on the append-only journal as `note_conflict` / `note_resolved` events.
`keep both` concatenates the two versions with a marker — nothing is discarded.

### Append-only journal groundwork (extended, not rebuilt)
`SyncEvent` / `SyncJournal` / `sync_log` from 0.5.0 S1–S2 are retained. Planner row writes now
emit `planner_projects`, `planner_tasks` and `planner_notes` upserts/deletes through the existing
`SyncJournal`; note conflicts add `note_conflict` / `note_resolved` records; the DAO gained a
per-entity cursor query and a `deleteAll()` used by full restore. Bulk paths (restore, merge,
seed, import) still deliberately do not journal.

## 0.5.2: discoverable tasks and richer Markdown

The 0.5.0 planner screen was reachable only from a button below the fold on Profile, so the
one-off tasks and Markdown notes were easy to miss. 0.5.2 adds:

- an always-visible **`+ task / note`** button in `AppScaffold` with a quick-add dialog for a
  one-off task, a Markdown note, or a direct jump to the full planner;
- a launcher long-press **planner shortcut** (`AppShortcuts`);
- deep links `planner?tab=tasks|projects|notes` so quick-add lands on the right tab;
- **task editing**, attachments, search, sort (created / due / priority / title) and a hide-done
  toggle in the planner's tasks tab;
- a visible **Markdown formatting toolbar** (headings, bold, italic, strike, code, quote, checkbox,
  ordered list, rule, table, image, link) in project/task/note editors and quick-add;
- parser/preview support for tables, images, strikethrough, ordered lists and horizontal rules,
  with new `PlannerLogicTest` coverage.

`AppScaffold` is not part of the screenshot suite's captured composables, and the planner screen has
no golden yet, so **no screenshot goldens were changed or regenerated**.

## 0.5.3: dedicated Planner tab and left drawer

The bottom bar now gives Planner its own fifth slot
(`today / habits / timer / watch / planner`). Profile moved out of the tab bar into a left
`ModalNavigationDrawer` behind a top `[≡ menu]` / settings control; a top-right `planner` button
and the existing `+ task / note` FAB remain as shortcuts. The wide-layout `SideRail` uses the same
tab set and links to Profile/Settings at its foot.

`StatusLine` defaults to `goldenTabs` (the original five tabs ending in Profile), while the real
app passes `appTabs` (ending in Planner). The one full-scaffold golden (`37-inner-split.png`)
renders `AppScaffold(..., goldenMode = true)`, which hides the new top bar/FAB, uses the legacy
rail and skips the drawer wrapper entirely so the captured layout is exactly the pre-0.5.3
scaffold; every other golden renders a single screen. **No screenshot goldens were changed or
regenerated** for this navigation change. `NavigationTabsTest` asserts both tab lists.

## Explicit boundary: DriveSync is NOT multi-device sync

`DriveSync` performs **full-archive backup/restore** (`.ptbak` / `.ptbakx`) plus the separate
two-way Markdown note mirror. There is **no event transport and no event replay** for `sync_log`,
so it must not be called multi-device sync. The journal is groundwork for a later transport;
roadmap item 7.3 stays open. Only after events are actually exchanged and replayed with
per-row last-writer-wins may the wording change.

## Release & validation

- `app.version=0.5` → `versionName 0.5.0`, then `v0.5.1` and `v0.5.2` patches. The CI release
  workflow derives the next free `v0.5.N` tag after a successful build; do not pre-create it.
- Upgrade gate: `MigrationTest` (1→11 and 10→11), `UpgradeTest` (every shipped schema 1…10 → 11,
  including planner rows and full gallery/document byte round trips), `LegacyBackupTest` (schema-1
  archive still restores), `ContractTest`.
- New pure tests: `PlannerLogicTest` (priorities, due dates, checklists, contextual refs, Markdown
  parser including tables/ordered lists/rules/strike/images, two-way conflict pause and both-version
  retention). 0.5.2 gate: 110 unit tests, full suite green.
- `git diff --check` must be clean; no force pushes; local `main` is preserved on
  `backup/pre-release-main-0f7d063` before the release branch is merged.

## Still open for a later V1.0 milestone

- 7.3 multi-device sync: implement event transport + replay, then update the wording above.
- Attachment re-linking after a content URI expires, and a WYSIWYG-style editor with cursor-aware
  formatting (0.5.2 has snippet insertion, not selection styling).
- Screenshot goldens for the new planner screen.
